## Correctness read-through

- **Handoff.** At every tracking-phase observation, the wrapper calls `tracker._progress(observation)` before `tracker.step`. `_progress` is pure: it reads `self.index` without mutating it, calls the pure `observed_distance`, and uses no RNG. So the pre-handoff commands and the RNG stream equal the unwrapped tracker's, as tested. The handoff check runs before the tracker's stall and termination checks, as declared. `handoff_row < L−1` is enforced, so `reference_complete` cannot occur before the handoff.
- **Replay start.** `cursor = frames[t]`, where `t` is the measured index. Action `i` turns frame `i` into `i+1` (same convention as `build_tracking_references`: close frame = first closing action + 1). So when the measured state matches row `t`, the next action is `frames[t]`. This is correct and not off by one. `len(actions) == frames[-1]` is validated, and a start at `frames[-1]` yields an immediate `demo_exhausted`.
- **Terminations.** `demo_exhausted` fires after the last action. A tracker termination before the handoff is mirrored, including `execution_rejected` set on acknowledgement. A replay `execution_rejected` is set both by the controller and by the worker loop. `step_limit` is the worker's default reason after 1,000 total loop commands. `replay_projection_rejected` and `execution_rejected` are not in `FAILED_TERMINATIONS`, so they count. Timeouts and runtime errors do not count.
- **Freshness and acknowledgement.** `_fresh` enforces strictly increasing observations across both the wrapper and tracker clocks. Replay acknowledgement requires the exact projected command and an advancing clock. An unacknowledged re-step is refused.
- **Worker.** The worker uses the same `PrivilegedRolloutModel` and `state_controller` path as TASK-045. The wrapper takes `actions_{demo.index}` from the verified library. Parity is counted from `privileged.pop_diagnostics()`, which is empty after the handoff because no `predict` or `encode` call happens. The last tracked command is therefore never parity-checked, as with any TASK-045 termination. `privileged.close()` runs in `finally`, and `hybrid.summary()` is merged into the report even after an error.
- **Gate.** Only `privileged_hybrid` drives `primary_gate_passed`. The early and `demo_replay` arms only feed their own readings (tested). The descriptive `conclusive` flag uses the complete-cohort predicate, the TASK-045 R1 lesson. `rollouts_exact` is computed over counted primary attempts only.

## Findings

**No blocking findings.**

Non-blocking findings, in order of importance:

1. **The R0 exception catch is broader than the protocol text.** `hybrid_phase.step` turns *any* `ContractError` raised by the projector into the counted `replay_projection_rejected`. `project_candidates` also raises `ContractError` for things that are not guard refusals: `validate_actions`, batch size, and "projection requires a current unconsumed observation". The protocol calls only guard refusals and infeasibility clean, and says a malformed projection stays a runtime error. These other errors are practically unreachable here: replay actions are finite clipped `[1,1,1,14]` float32, and the worker observes immediately before `step`. The reason string is recorded, so every case can be audited. Fix, preferably before the run: re-raise unless the message is the embodiment's `measured joint velocity limit exceeded` guard, or classify by a guard-error type. Otherwise, add one sentence to the protocol before running: any `replay_rejection.reason` other than that guard or `no feasible projection` is a software finding, and that attempt is treated as uncounted.
2. **Misleading tracking diagnostics in the hybrid per-reset rows.** Replay traces carry no `reference_index`, so `last_reference_index` stays at the last *tracked* planning index, which is below the handoff row. `_tracking_row` then reports `stalled_before_close_reference = True` for every non-grasp primary reset, even when it handed off at or past the close row. `passed_demo_grasp_reference_without_grasp` is always False. These fields do not feed any hybrid reading. Fix: drop these two keys in `_hybrid_arm`, or set `last_reference_index` from `handoff_reference_index` at the handoff. Failing that, the results document must use `handoff_reference_index` and ignore these two fields.
3. **The early-arm replay start can be later than frame 136–137.** The measured index can exceed `handoff_row` by up to the 16-row window. The protocol's justification (point 2: "Replay starts at frame 136–137, so it includes the whole blocked descent") holds only if the handoff lands exactly on the row. TASK-045's 43002 and 43003 crossed close−16 only 4 and 3 commands before the close row. The design text (`f = frames[t]`) is correct, and `handoff_frame` is recorded. Fix: reword to "frame ≥ 136–137", and report the actual `handoff_frame` for each reset in the results.
4. **Guard stops are pooled into one reading.** `replay_from_tracked_state_insufficient_for_grasp` counts `replay_projection_rejected` together with fully replayed no-grasp attempts. That is consistent with the reading's meaning, since a guard stop from the tracked state is itself a state mismatch. But the results should report the split (`demo_exhausted` vs `replay_projection_rejected`, and the rejecting frame) per reset.
5. **R0 disclosure details.** R0 also reclassifies an *infeasible* replay projection from runtime error to clean termination. The design bullets say this, but the R0 paragraph mentions only guard refusal. The code is also asymmetric: a guard refusal *during tracking*, or in `demo_replay`, is still an uncounted `runtime_error`, because those paths are unchanged. Add one line to each point in the results. Neither changes a threshold.
6. **Provenance is run-wide.** An input-hash failure during a later arm marks all earlier records invalid (inherited supervisor semantics). So the statement "secondary arms never change the primary gate" holds for outcomes but not for provenance. This is acceptable because changed inputs invalidate the run. State it in the results if it happens.
7. **Run commit.** The frozen command says "from a clean checkout of the reviewed commit". Committing this review creates a new, documentation-only HEAD. Run from that commit, and record its SHA together with the fact that it differs from `e230884` only in `docs/reviews/`, plus whatever fix is chosen for finding 1 or 2.

## Scientific readiness

The primary hypothesis and gate are sensible and bounded. The gate is ≥2/4 grasp for the close-row handoff, with exact rollouts and valid provenance. The reference is open-loop replay from reset, which grasps 4/4. The protocol honestly states that the hypothesis was motivated by development outcomes on the same resets and is not a held-out test. The secondary offset of 16 is the existing horizon and progress window, with a first-principles argument. I verified that argument: with H16 targets `t+1…t+16` planned at `t ≤ close−17`, no executed tracked command targets a closing row. The argument is not drawn from development traces. The TRAIN numbers it cites are correct. The comparison table correctly limits itself to associations over n = 4 that do not isolate a mechanism.

R0 is justified and fairly disclosed. It was decided after a TRAIN-reset smoke, not a development reset. It changes only whether a physical guard stop is counted, so it can make results more conclusive but cannot turn a failure into a grasp. The handoff rows, gate, thresholds, budgets, seeds and command are identical between `0c419e4` and `e230884` (verified by diff).

The attribution rule is fixed up front: any post-handoff stage comes from replayed demonstration actions, and nothing before the handoff is learned either. Every interpretation branch is labelled NON-LEARNED. The pass branch names the next learned replacement: learned `state_goal_sensor_wm_v1` approach dynamics to the same handoff, with `dynamics_shuffle`/`persistence` controls, in a separately preregistered task. It also says demonstration memory is not a model. TASK-033/034 stay open, and 44000–44019 and TEST stay untouched.

The budget is sound. Mode-major order runs the primary arm first, and 4 × 840 s = 3,360 s < 3,600 s, which leaves about 235 s for preparation (about 5–10 s observed). Timeouts and global shortening count 0 and make that arm inconclusive. Expected totals from TASK-045 and TASK-043 timings (about 2,100 s) are plausible.

The TRAIN smoke is a strong negative prior. On the reset whose retrieved demonstration is its own recording, neither hybrid arm grasped. The primary arm hit the velocity guard and the early arm dropped the apple. A primary failure should therefore not be reported as surprising, and the post-run write-up must not retune the handoff from it. The protocol already forbids that. The run still discriminates between the declared failure readings and checks the `demo_replay` reference under current code.
